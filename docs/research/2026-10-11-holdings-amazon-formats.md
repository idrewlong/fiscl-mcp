# What are the real file formats for fiscl Phase 4 importers (broker holdings, crypto tax reports, Amazon order history, QIF)?
Date: 2026-10-11 23:00 · Author: my-skills:researcher · Requested by: orchestrator (spec `specs/2026-10-11-2224-v2-phase4-data.md`, R5/R6/R10) · Status: partial (no vendor publishes header rows; most evidence is community parsers and sample files; crypto vendor headers largely unverified)

## Answer (TL;DR)
- **Brokers:** Fidelity, Schwab and Vanguard each need different preamble/footer handling that the current profile model (`skip_rows` only) cannot express. Fidelity has a footer (`Date downloaded ...`) and the full account number in column 1. Schwab has a preamble line (with the snapshot date, masked account) plus summary rows at the bottom. Vanguard has no date at all, the full account number in column 1, and two CSV sections in one file. Confidence: medium-high for Fidelity and Schwab (several independent parsers and sample files, one from Dec 2025), medium for Vanguard (older sources; no cost basis in the holdings section).
- **Crypto:** For a holdings snapshot, use the CoinLedger EOY Positions or Koinly End-of-Year Holdings CSV. For realized gains, use the Capital Gains CSVs. I could not verify exact header rows for Koinly, CoinTracker, TokenTax or ZenLedger from any primary or reliable secondary source. Do not ship built-in crypto profiles until a user supplies a header row. "Solana tax engine export" is not defined anywhere in the repo or on the web; ask the owner. Confidence: low on headers, high on report-purpose mapping for Koinly and CoinLedger.
- **Amazon:** The path is Account > Data and privacy > Request your data > "Your Orders". There are at least three header variants in the wild, so the spec's single header-set constant is too narrow. Rows are per item, not per shipment or order. Charge-to-transaction mapping is unverified; two open-source tools disagree on grouping. Confidence: medium on the main 28-column layout, low on `Total Owed` semantics and payment last4.
- **QIF:** Field codes, section types, `!Account` and split lines are confirmed. The spec has no authoritative date rules, so the spec's "US default plus explicit flag plus hard failure on day > 12" approach is the right design. Confidence: high on structure, medium on apostrophe-year semantics.

## Findings

### 1. Brokerage positions exports

None of the three brokers documents the CSV layout in its help center. The evidence is community importers and sample files, so treat every header below as "seen in the wild", and have the owner confirm against one real file (scrub the numbers) before shipping a built-in profile.

#### Fidelity (Accounts > Positions > three-dot menu > Download)
- Filename: `Portfolio_Positions_<Mon-DD-YYYY>.csv` (importer filename pattern `Portfolio_Positions_.*.csv`, [beancount_reds_importers fidelity_all_account_positions_csv.py](https://github.com/redstreet/beancount_reds_importers)). The Fund Manager docs call the position file `*Positions*.csv`.
- Encoding: UTF-8 with BOM (importer sets `utf-8-sig`).
- Header (regular view), two generations seen:
  - Older/sample: `Account Number,Account Name,Symbol,Description,Quantity,Last Price,Last Price Change,Current Value,Today's Gain/Loss Dollar,Today's Gain/Loss Percent,Total Gain/Loss Dollar,Total Gain/Loss Percent,Percent Of Account,Cost Basis Total,Average Cost Basis,Type` (16 columns; sample file in [frizille/trading-port-summary examples/sample_positions.csv](https://github.com/frizille/trading-port-summary), built by someone who parses real files, synthetic data). Note: the beancount importer's own constant spells `Last price`/`Current value` in lowercase, so match case-insensitively.
  - Newer (17 columns): inserts `Investment Type` after `Account Name` ([AojdevStudio/Finance-Guru portfoliosyncing skill](https://claudskills.com/skills/portfoliosyncing/SKILL.md)).
  - Dividend view (different column set, 19 columns, has `Ex-date`, `Est. annual income`): must be rejected or ignored; it lacks cost basis.
  - Users can customize columns ("My View"), so column sets vary. Detect by header names, never by position.
- Every data row ends with a trailing comma (extra empty column), as in the sample.
- Footer (after the last position row): one blank line, then two quoted lines: a disclaimer ("The data and information in this spreadsheet is provided for informational purposes only...") and `"Date downloaded Dec-05-2025 at 1:02 p.m ET"` (format in the Dec 2025 importer: regex `Date downloaded (Mon-DD-YYYY)`, `strptime("%b-%d-%Y")`). The sample uses `Date downloaded Jan-15-2026 10:00 a.m ET`. So the snapshot date is in the file footer (and the filename is `Portfolio_Positions_Dec-05-2025.csv`, per the matching pattern).
- Account identifiers: **full account number in column 1** (e.g. `Z11111111`, or `86689` for a 401k plan) plus the account nickname in `Account Name`. fiscl must drop `Account Number` (or keep at most the last 4) and never persist the rest.
- Number formats (sample, medium confidence): currency `$5000.00` (no thousands commas in the sample; do not assume that), signed deltas `+$1.00` / `-$2.00`, percents `+0.46%`, shorts as negative quantity (`-1`). Missing values are blank, not `--`, in this sample; `--` appears in real exports for some cells (Fidelity "n/a" cells), so treat `--` and blank as null. Parser caution: the beancount importer strips everything except `[0-9.]`, which silently loses minus signs; do not copy that.
- Cash/money market: core position row such as `SPAXX**` with `Description` "HELD IN MONEY MARKET", blank Quantity and Last Price, only `Current Value` filled, `Type` = `Cash`. Also a synthetic-looking row `Pending activity` (Current Value only, no symbol-like data). The Finance-Guru skill warns the SPAXX value in the positions CSV reflects only settled money market funds, versus the Balances CSV. Other cash symbols seen: `FDRXX`, `FCASH`. Note the `**` suffix on the symbol.
- `Type` column is `Cash` or `Margin` (account type of the lot), not asset class. Crypto appears as `BTC/USD`, `ETH/USD` symbols (slash). Options appear with a leading space and dash: ` -AAPL260116C240`. Bonds/CDs/core funds can carry CUSIPs in `Symbol`. Muni bond share counts can be reported 100x (importer has a "fix_muni_shares" workaround).
- Quantity can be fractional (e.g. `4.447`, `72.942`).

#### Schwab (Accounts > Positions > Export; also reachable at `client.schwab.com/api/PositionV2/PositionsDataV2/Export?format=csv`, per [jbms/finance-dl schwab.py](https://github.com/jbms/finance-dl/blob/master/finance_dl/schwab.py))
- Filename: `<Account name>-Positions-YYYY-MM-DD-HHMMSS.csv` (e.g. `Roth Contributory IRA-Positions-2026-04-19-135949.csv` in [juheo1/stock_screener plan](https://github.com/juheo1/stock_screener); importer pattern `.*-Positions-`).
- Layout (confirmed by 4 independent parsers):
  1. Line 1 (preamble): `"Positions for account <Name> ...NNN as of 10:45 AM ET, 2026/05/11"`. The date is the last token, `YYYY/MM/DD` (beancount importer `date_format = "%Y/%m/%d"`; [cohenjo/trading-journal schwab-csv-parser.ts](https://github.com/cohenjo/trading-journal)).
  2. Line 2: blank.
  3. Line 3: header, all values quoted, trailing comma.
  4. Position rows (quoted values, trailing comma).
  5. Summary rows to skip: `Cash & Cash Investments` (this is the cash/money market line; it has a market value but no quantity) and `Positions Total`. Multi-account ("All-Accounts") exports repeat sections and use `Account Total`; I did not confirm the exact all-accounts layout. Skip `Account Total` as well.
- Header (two layouts seen; match by name):
  - `"Symbol","Description","Price","Qty (Quantity)","Price Chng $ (Price Change $)","Price Chng % (Price Change %)","Mkt Val (Market Value)","Day Chng $ (Day Change $)","Day Chng % (Day Change %)","Cost Basis","Gain $ (Gain/Loss $)","Gain % (Gain/Loss %)","Ratings","Reinvest?","Reinvest Capital Gains?","% of Acct (% of Account)","Asset Type"` (current layout in the beancount importer; also `Div Yld (Dividend Yield)` in some views per trading-journal).
  - Older/alternate: `"Symbol","Description","Quantity","Price","Price Change %","Price Change $","Market Value","Day Change %","Day Change $","Cost Basis","Gain/Loss %","Gain/Loss $","Ratings","Reinvest Dividends?","Capital Gains?","% Of Account","Security Type"`. Note the column order differs (Price before Qty in the new layout).
  - Use `Symbol`, `Description`, `Qty (Quantity)` or `Quantity`, `Price`, `Mkt Val (Market Value)` or `Market Value`, `Cost Basis`, `Asset Type` or `Security Type` aliases.
- Account identifiers: the account label and **masked last digits** (`...051`) are in the preamble only; no account number column. This is the safest of the three; the filename may contain the account nickname.
- Number formats: `$1,373.00`, `-$69.00`, percents `16.64%`, and `--` or `N/A` for missing (trading-journal and beancount importer treat `--` as null). Thousands commas present. Cost basis is total, not per share (stock_screener plan derives per-share as Cost Basis / Qty).
- Asset Type values seen: `Equity`, `ETFs & Closed End Funds`, `Cash and Money Market` (the last should be treated as cash).

#### Vanguard (Download Center / Balances > Download > "Download CSV (spreadsheet)"; file is named `OfxDownload.csv` despite the name)
- Official docs: none found. The file is a **two-section CSV** (per [hledger vanguard.csv.rules](https://github.com/simonmichael/hledger) and [geemus/prototypes investing.rb](https://github.com/geemus/prototypes)):
  1. Holdings section: header `Account Number,Investment Name,Symbol,Shares,Share Price,Total Value,` (trailing comma), then one row per holding across all accounts, e.g. `<acct>,VANGUARD S&P 500 INDEX ETF,VOO,18.1817,629.3,11441.74,` ([Finance-Guru retirement-syncing skill](https://github.com/AojdevStudio/Finance-Guru)).
  2. A blank line, then a transactions section with header `Account Number,Trade Date,Settlement Date,Transaction Type,Transaction Description,Investment Name,Symbol,Shares,Share Price,Principal Amount,Commission Fees,Net Amount,Accrued Interest,Account Type,` (15 fields).
- No cost basis, no snapshot date in the file, and no preamble. The as-of date must come from the filename's download time (the file is usually just `OfxDownload.csv`, so effectively the CLI `--as-of`). Cost basis requires a separate Vanguard "cost basis" download (not researched).
- Account identifiers: **full account number in column 1** (digits, e.g. 8 digits). fiscl must discard or truncate to last 4. One file covers all accounts, so a holdings import must split by account number and map each to a fiscl account (the spec's single `--account` flag does not fit).
- Numbers are plain (`629.3`, `11441.74`, no `$`, no commas observed). Money market funds (e.g. `VMFXX`) appear as normal rows with Share Price 1.00. Cash held outside a fund is not a row in the holdings section (unverified).
- Vanguard's OFX/QFX route for third-party apps is currently disabled/unreliable ([Fund Manager forum, Jan 2026](https://fundmanagersoftware.com/forum/viewtopic.php?p=28508)); CSV is still the route.

#### What this means for `csv_import.py` / the profile model
- `Profile.skip_rows` (an int, `src/fiscl/importers/csv_import.py`) only handles leading lines. These files need: a **header-row finder** (Schwab header is line 3; Vanguard holdings header is line 1 but data ends at a blank line), **stop-at-blank-line** (Vanguard section 2; Fidelity footer), **skip-symbol list** (`Cash & Cash Investments`, `Positions Total`, `Account Total`, `Pending activity`), **trailing comma tolerance** (all three), **BOM**, and **as-of extraction** from the file (Fidelity footer regex, Schwab preamble regex, none for Vanguard).
- `parse_amount` must accept `$`, thousands commas, leading `+`/`-` before `$`, `%`, `--`, `N/A`, blank, and parentheses (parentheses not seen in these three, but common elsewhere).
- Because of full account numbers (Fidelity, Vanguard), the holdings importer should never copy the account column into `raw_description`-like stored text; add a test with a synthetic 9-digit number asserting it is not persisted.

- Form 8949-style CSVs from tax software generally follow IRS columns (a)-(h): description (e.g. `1.5 SOL`), date acquired, date sold, proceeds, cost basis, adjustment code, adjustment amount, gain/loss. NODE40's import format is `Description, Date Acquired, Date Sold, Proceeds, Cost Basis, Adjustment Code, Adjustment Amount, Term` ([NODE40 KB](https://node40.atlassian.net/wiki/spaces/NKB/pages/3460169730/Understanding+the+IRS+8949+Form+and+Addendum+Files)). This is a third-party tax-software format, not a crypto vendor export. Useful only as a generic realized-gains target shape.
- Exchanges (Coinbase, Kraken): not researched to a verified conclusion. From general knowledge (unverified here), both provide transaction-history CSVs and Coinbase offers a gain/loss report; neither gives a clean holdings-with-cost-basis export. I would not build profiles for them.
- **"Solana tax engine export":** appears only in `docs/PROJECT.md:200` ("Brokerage holdings CSV, crypto (Solana tax engine export) | v2 | Positions and cost basis") and in the spec (R5). No definition in the repo, git history (`git log -S"Solana"` finds only the v1 baseline commit), or on the web. Could be the owner's own script/tool, a Solana-focused tax product, or a loose phrase. **Needs the owner to answer or supply a header row.** Do not guess a profile.
- Best report for fiscl's `holdings` tool: a holdings snapshot with cost basis. That is CoinLedger EOY Positions (cost basis remaining per lot, no price; fiscl would need `price` from... nowhere, since the spec forbids price fetching, so value would be unavailable) or Koinly End of Year Holdings (has value and cost). Realized gains belong to Phase 3 tax tools, not `holdings`. Note a gap: a year-end snapshot is as-of Dec 31 of the tax year, not today.

### 3. Amazon order history

- **How to get it (confirmed by 3 secondary sources, none from Amazon; last verified 2026-09-28):** Amazon account > Data and privacy (Privacy Central, `amazon.com/hz/privacy-central/data-requests/preview`) > "Request your data" > pick only "Your Orders" (recommended; "request all" is bigger and slower) > confirm by email > download the ZIP within the link's validity window (reports say ~30 days) > unzip. Typical wait: hours to 3 days, up to 30 days. Sources: [Takeout Day](https://takeoutday.org/guides/how-to-download-amazon-data), [Tiller](https://tiller.com/?p=137473). The old one-click "Order History Reports" page is gone or region-limited.
- **File name varies:** `Your Orders/Retail.OrderHistory.1/Retail.OrderHistory.1.csv` (purchases; Tiller, [mint-amazon-tagger](https://github.com/jprouty/mint-amazon-tagger), [hbmartin/amazon-to-sqlite](https://github.com/hbmartin/amazon-to-sqlite)), `Retail.OrderHistory.2/...` (additional file, [Amalytix](https://www.amalytix.com/en/tools/amazon-order-analysis/); [wesm/moneyflow](https://github.com/wesm/moneyflow) reads all `Retail.OrderHistory.*.csv`), and one 2026 guide reports `Your Orders/Order History.csv`. Returns are a separate file (Tiller). Nested subfolders: the importer must accept the file directly (the spec already dispatches by header, good) and ideally a directory.
- **Header (28 columns, order as published by Amalytix for `Retail.OrderHistory.2.csv`; Tiller lists the same order for the "old" file):** `Website, Order ID, Order Date, Purchase Order Number, Currency, Unit Price, Unit Price Tax, Shipping Charge, Total Discounts, Total Owed, Shipment Item Subtotal, Shipment Item Subtotal Tax, ASIN, Product Condition, Quantity, Payment Instrument Type, Order Status, Shipment Status, Ship Date, Shipping Option, Shipping Address, Billing Address, Carrier Name & Tracking Number, Product Name, Gift Message, Gift Sender Name, Gift Recipient Contact Details, Item Serial Number`. Mint-tagger notes a quoting bug on the first column (`Website"`).
- **Variant (Tiller, May 2023):** a newer file renamed `Quantity` > `Original Quantity`, `Payment Instrument Type` > `Payment Method Type`, `Gift Recipient Contact Details` > `Gift Recipient Contact`, `Total Owed` > `Total Amount`, plus two junk columns `Column 1`, `Column 2`. This contradicts Amalytix, which shows `Total Owed` / `Payment Instrument Type` in a `.2.csv`. Both may be real (different request cohorts/dates). **The importer must alias these names.**
- **Row grain:** one row per item (not per order, not per shipment). Multi-item orders yield multiple rows (Amalytix).
- **Value formats:** money as plain decimal strings in `Currency` (mint-tagger parses as USD, strips `$`/commas); dates ISO-like with `Z` (e.g. `2023-01-05T14:22:10Z`; mint parses with dateutil), `Order Date` and `Ship Date` both; missing values literally `Not Available`; `Ship Date` is `Not Available` for unshipped; `Payment Instrument Type` and `Carrier Name & Tracking Number` and dates can hold multiple values joined with ` and ` (mint-tagger splits on `" and "`); addresses masked.
- **Payment last4:** I found no source showing the card last4 in `Payment Instrument Type`. The column is a type string (documented examples only name the field). Treat last4 as **not available**; the spec must not depend on it. (Unverified: some exports show values like "Visa - 1234"; get a real sample.)
- **Amount semantics (unverified, conflicting):** mint-tagger's docstring: `shipment_item_subtotal = unit_price*quantity + other items in same charge`; `total_owed = shipment_item_total + shipping_charge + total_discounts`. Amalytix's sample shows `Shipment Item Subtotal` (55.65) larger than a single item's price (7.47), i.e. shipment-level, repeated on each item row of the shipment, so summing it across rows double-counts. `Total Owed` in the sample (8.89) equals unit price + tax for a single-item row, so it looks per-item. Whether shipping/discounts are apportioned per item or only on one row is not established.
- **Mapping charges to card transactions:** Amazon charges the card per shipment (commonly) so one order can create several card charges and one charge can cover several items. Evidence of approaches: mint-amazon-tagger builds a "Charge" = items from one order with the same shipment (never across order IDs), and handles partial gift-card payment and hidden state fees. [wesm/moneyflow](https://github.com/wesm/moneyflow) matches a bank charge to the **whole order** within 0.02, then to a smaller charge consistent with gift-card use (difference at most max(15, 10% of order)), then per item, with a 7-day window. These are community heuristics; Amazon publishes no mapping.

### 4. QIF

- **Authoritative references:** The original Intuit spec is only available from the Wayback Machine (`web.archive.org/web/20100222214101/http://web.intuit.com/support/quicken/docs/d_qif.html`, per [Wikipedia](https://en.wikipedia.org/wiki/Quicken_Interchange_Format); the Wayback host is blocked from this tool, so not read directly). The W3C-hosted copy at [w3.org QIF-doc](https://www.w3.org/2000/10/swap/pim/qif-doc/QIF-doc.htm) was read in full for the items below.
- **Section headers:** `!Type:Bank`, `!Type:CCard`, `!Type:Cash`, `!Type:Oth A` (asset), `!Type:Oth L` (liability), `!Type:Invst`; lists `!Type:Cat`, `!Type:Class`, `!Type:Memorized`, `!Account`; `!Type:Invoice` (Quicken Business). `!Option:AllXfr` is the only option the W3C doc names; `!Option:AutoSwitch` / `!Clear:AutoSwitch` appear around account lists in real Quicken exports (from general knowledge; not in either source I could read, so parser should ignore any unknown `!Option:`/`!Clear:` line).
- **Fields for Bank/CCard/Cash/Oth A/Oth L:** `D` date, `T` amount (`U` is a duplicate in some exports), `C` cleared (`*`/`c` cleared, `X`/`R` reconciled), `N` check number, `P` payee, `M` memo, `A` address (up to 5 lines), `L` category (`Category:Sub/Class`; **transfers as `[Account Name]`**), `F` reimbursable flag, `^` end of record.
- **Splits:** `S` split category, `E` split memo, `$` split amount, optional `%` split percent; repeat `S`/`E`/`$` per split; the transaction's own `T` is the total. In investment records `$` is the transfer amount.
- **`!Account` block:** `N` name, `T` type (e.g. `TBank`, `TCCard`, `TInvst`), `D` description, `L` credit limit (cards), `/` statement balance date, `$` statement balance, `^` end. Appears (a) at the start of an account list and (b) before a transaction list to say which account the following `!Type:` section belongs to. This matches the spec's "No `account_key`; use `!Account` name" approach.
- **Amounts:** negative with leading minus, thousands commas (`T-1,000.00`).
- **Dates (no authoritative rule; observed forms):**
  - `M/D/YY` (`D8/25/93`), padded with spaces: `D6/ 1/94`, `1/ 2'26`.
  - `M/D'YY` and `M/D'YYYY` (Wikipedia sample `D2/10'2020`): the apostrophe marks a post-1999 two-digit year in Quicken output (Y2K change; semantics from community, "workaround to differentiate the century", [KMyMoney thread via search](https://forum.kde.org/viewtopic.php%3Ff=69&t=176355.html)). Treat `'YY` as 2000+YY (matches the spec), and `/YY` with YY <= 99 as spec'd (2000+) but note pre-2000 files exist.
  - `D/M/YYYY` or `DD/MM/YYYY` in non-US locales; KMyMoney was reported exporting dotted `DD.MM.YYYY` ([KDE bug 230124](https://bugs.kde.org/show_bug.cgi?id=230124)).
  - Spelled form in the Wikipedia examples (`D25 December 2006`) is rare.
  - No file declares its date order; the only fix is a user flag or cross-checking that all dates parse under one order ([Manager.io thread](https://forum.manager.io/t/imported-bank-statements-for-a-single-date-converts-the-dates/14332)).

## Contradictions and gaps versus the spec (`specs/2026-10-11-2224-v2-phase4-data.md`)
1. **Holdings, as-of date (spec line 46):** spec offers only `as_of_column` or CLI `--as-of`. Fidelity and Schwab carry the date in a footer/preamble line, not a column, so a column-only model forces the CLI flag. Add an as-of extraction rule (regex on a preamble/footer line plus date format) to the profile. Vanguard has none.
2. **Holdings, file structure (spec line 46, `skip_rows`):** leading-skip only. Need header-row discovery, stop-at-blank / footer skip rows, skip-symbol list, trailing-comma and BOM handling (see section 1).
3. **Account numbers:** Fidelity and Vanguard files contain full account numbers in column 1; spec says "never store full account numbers" elsewhere. The importer must not persist this column and the spec's DoD needs a test. Vanguard also mixes multiple accounts per file, which conflicts with the single `--account` assumption (spec line 47).
4. **Cost basis:** Vanguard holdings section has none; CoinLedger EOY positions has remaining cost basis per lot but no price/value. Spec's `value_column?`, `price_column?` optional is right, but the `holdings` tool must handle lot rows (multiple rows per symbol) by summing.
5. **Short positions and cash rows:** Fidelity options have negative quantity and a leading space/dash symbol; SPAXX-style rows have blank Quantity. Spec's `asset_class_column` may map Schwab `Asset Type` only; Fidelity has none (`Type` is Cash/Margin, `Investment Type` in newer files).
6. **Amazon header set (spec line 89):** working assumption (`Order ID`, `Order Date`, `Ship Date`, `Product Name`, `Quantity`, `Total Owed`, `Currency`) matches the 28-column layout, **but** a documented variant renames `Total Owed` > `Total Amount` and `Quantity` > `Original Quantity`, and a 2026 guide reports the file as `Order History.csv`. Detection must tolerate aliases. `Not Available` dates and ` and `-joined multi-values need handling.
7. **Amazon grain and dedupe (spec line 89):** rows are per item; the spec's row dedupe `(order_id, product_name, ship_date, total)` plus occurrence index is reasonable. But `Shipment Item Subtotal`/`...Tax` are shipment-level and repeated, and whether `Total Owed` includes shipping/discounts per item row is unverified; the spec's "3-item shipment totaling $61.16" proposal logic (groups by shipment) depends on this. **R6 stays open: one real scrubbed row set is still needed**, preferably a multi-item shipment with shipping and a gift-card partial payment.
8. **Amazon payment last4:** not available as far as evidence shows; do not rely on it for matching (spec relies on amount + date window, which is fine).
9. **QIF:** spec covers `Bank/CCard`, skips `Invst`. Add explicit handling for `Oth A`/`Oth L` (asset/liability account types), and skip `!Type:Cat`, `!Type:Class`, `!Type:Memorized` and unknown `!Option:`/`!Clear:` lines. Dotted `DD.MM.YYYY` dates exist from KMyMoney exports; spec date forms (line 41) don't list `.`. `U` as alias of `T`. The spec's day>12 hard failure is well supported by the sources.
10. **R5 "Solana tax engine export":** unresolved; owner decision still required.

## Recommendation
1. Ship `generic-holdings` first, as specced. Add Fidelity and Schwab built-ins (header-name aliases, footer/preamble as-of, skip symbols) only after the owner supplies one scrubbed header + two rows from each real file; use the formats above to write synthetic fixtures. Vanguard: needs per-row account mapping and CLI `--as-of`; defer until the multi-account question is decided.
2. Extend the holdings profile fields before slice 2: `header_match`/`header_row_finder`, `stop_at_blank`, `skip_symbols`, `as_of_regex` + `as_of_format`, `account_column_policy = "ignore" | "last4"`.
3. Crypto: make no vendor profile without a real header sample. Ask the owner what "Solana tax engine export" is and which tool they actually use.
4. Amazon: put all column names in one alias table (`Total Owed|Total Amount`, `Quantity|Original Quantity`, `Payment Instrument Type|Payment Method Type`); parse `Not Available` as null; accept the CSV directly; group by `(order_id, ship_date)` for charge matching and keep the "exact match only" rule (R7). Get a real sample before finalizing the amount math.
5. QIF: implement as specced with the additions in contradiction 9.
What would change this: a real Fidelity/Schwab/Vanguard sample showing a different header, or an Amazon sample showing that `Total Owed` is shipment-level.
