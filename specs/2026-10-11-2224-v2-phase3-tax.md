## Goal
A sole proprietor can hand their preparer a Schedule C package per business (CSV + Markdown in `~/fiscl/exports/`) that includes home office (simplified method), mileage, and meals, can see state estimated-tax dates and a planning-rate state estimate next to the federal one, and can reconcile the 1099-NEC/1099-K forms they received against the business income fiscl sees. Every output stays framed as records and questions for the user and their preparer, never advice.

## Non-goals
- PDF export (later; needs a dependency decision). Filling the official IRS form or e-filing.
- A state income-tax engine: no brackets, credits, local taxes, residency or part-year logic. Planning rate only (roadmap Risks, confirmed direction 2026-10-11).
- Home office regular (actual-expense) method, Form 8829, depreciation of the home.
- COGS / Part III, depreciation schedules, health insurance, QBI, Additional Medicare tax.
- Pulling 1099 data from anywhere. The user types the amounts in.
- Writing files anywhere except `<data dir>/exports/`. No user-supplied paths or filenames.
- Per-business categories. Categories and Schedule C line mapping stay global.

## Design decisions (locked unless noted)
1. **`tax.py` becomes a package** (mirrors the 2026-10-11 analysis refactor decision): `src/fiscl/tax/__init__.py` re-exports every public name so `from fiscl import tax; tax.schedule_c_draft` and `from fiscl.tax import DISCLAIMER` keep working. Modules: `tax/schedule_c.py` (lines, draft), `tax/estimates.py` (federal + state), `tax/review.py`, `tax/edits.py` (`set_scope`, `log_trip`, `mileage_log`), and new `tax/home_office.py`, `tax/export.py`, `tax/forms1099.py`, `tax/states.py` (data table), `tax/businesses.py` (slice D). This lets slices land in parallel worktrees with conflicts only in `server.py` and `tax/__init__.py`.
2. **Home office lives in `config.toml`**, per tax year, like the other tax settings the user enters once. Read-only from tools in this phase (no TOML-writing tool).
3. **Exports are dry-run by default** and never overwrite: filenames are built only from fixed tokens, the year, a business id, and a timestamp; files are opened with `O_CREAT | O_EXCL | O_NOFOLLOW` and mode 0600.
4. **State estimates reuse the federal planning-rate pattern.** A static table keyed by two-letter code gives due dates, installment percentages, and a no-income-tax flag, with a `verified_for` year.
5. **1099 reconciliation produces questions, not conclusions.** Matching is by user-provided payer → merchant mapping, never fuzzy guessing presented as fact.

## Contract

All tools return `meta`. Money args are dollars (parsed with `common.money_arg`); money in responses is `{"minor", "display"}`. Tax tools add `"disclaimer": DISCLAIMER` (or put it first in `notes`, as today). "W" = local write, `dry_run=True` default, returns `common.plan_result(...)`. Errors are `GuardError` with fixed prose and a code; never a payer, business, merchant name, or amount in the message.

### Changed tool: `schedule_c_draft` (READ_ONLY)
Args: `{year?: int, business?: str}` (`business` arrives with slice D; until then it is not accepted).
Response additions:
```json
{
  "business": {"id": 1, "name": "My business"},          // slice D; omitted before
  "home_office": {
    "method": "simplified",
    "square_feet": 200, "months_used": 12,
    "allowable_square_feet": "200.0",                     // sqft × months_used / 12, 1 dp, ≤ 300
    "rate_per_sqft": {"minor": 500, "display": "$5.00"},
    "computed": {"minor": 100000, "display": "$1,000.00"},
    "limited_to_profit": false,
    "line_30": {"minor": 100000, "display": "$1,000.00"}
  },                                                       // null when not configured for the year
  "tentative_profit_before_home_office": {...},
  "net_profit": {...}                                      // tentative_net_profit kept as an alias = net_profit
}
```
Rules: `computed = round_half_even(allowable_sqft × 500)` minor; `line_30 = min(computed, max(tentative_profit_before_home_office, 0))`; `limited_to_profit = line_30 < computed` with a note ("The simplified home office deduction can't exceed the business's gross income minus other expenses; the unused part does not carry over under this method."). The old "Home office (line 30) … not computed" note is replaced by "Home office uses the simplified method only…" when configured, and by "No home office configured for {year}; add [tax.home_office.{year}] if you use part of your home regularly and exclusively for business." when not. `estimated_tax` uses `net_profit` (after line 30).

### New tool: `export_schedule_c` (W — `LOCAL_WRITE`, `idempotentHint=false`: additive, never overwrites)
Module `tax/export.py`.
Args:
```
{ "year": int?,                      // default current year (year_bounds)
  "business": str?,                  // slice D; default = every business with activity, one file set each
  "formats": ["csv","markdown"]?,    // default both; enum-validated
  "include_transactions": bool?,     // default false; adds a detail CSV
  "dry_run": bool = true }
```
Dry-run response:
```json
{ "dry_run": true,
  "files": [ {"path": "exports/schedule-c-2026-b1-20261011T222400.csv", "kind": "summary_csv", "rows": 24},
             {"path": "exports/schedule-c-2026-b1-20261011T222400.md", "kind": "markdown"},
             {"path": "exports/schedule-c-2026-b1-20261011T222400-detail.csv", "kind": "detail_csv", "rows": 311} ],
  "summary": { "gross_receipts": {...}, "total_expenses": {...}, "net_profit": {...} },
  "next_step": "Call again with dry_run=false to write these files.",
  "notes": [DISCLAIMER, ...], "meta": {...} }
```
Applied response: same, `dry_run: false`, plus `"written": true`, `"data_dir_relative": true`. Paths are always relative to the data dir (no absolute paths, so the username doesn't leave the machine via the model).
- **File naming:** `schedule-c-{year}-b{business_id}-{YYYYMMDDTHHMMSS}[-detail].{csv|md}`. Before slice D, `b1` is used (default business id). Business names never appear in filenames.
- **Writing:** `exports/` created by `ensure_layout` (0700). Before writing: `exports` must be a real directory (not a symlink; `os.lstat`), owned by the user, under `cfg.home` after `resolve()`. Open with `os.open(path, O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW, 0o600)`; on `FileExistsError` raise `GuardError("an export with that name already exists; try again in a second", code="exists")`. All files of one call are written to `*.tmp` (same flags) then `os.replace`d, or all removed on error.
- **Summary CSV** columns: `section,line,line_name,category,amount,full_amount,count,note`. Rows: gross receipts (line 1), each line with per-category rows, line 9 standard mileage row, line 24b with `full_amount`, line 30 home office, `total_expenses`, `net_profit`, `unmapped` rows, then `disclaimer` and `data_through` rows. Amounts are plain decimal strings (`1234.56`, `-45.00`), no currency symbol.
- **Detail CSV** columns: `date,account,merchant,amount,category,line,scope,business,note,transaction_id,split_id`, one row per `txn_lines` business-scope line in the year (split children are separate rows).
- **CSV injection:** every text cell (category, merchant, account, note, business, line_name) whose first character is one of `= + - @ \t \r` or a full-width variant (`＝ ＋ － ＠`) is prefixed with `'`. Numeric cells are written as numbers only. Bank text goes through `guard.clean_text` first.
- **Markdown:** title, disclaimer blockquote, data freshness, a table per section. Every text value is escaped: `\ ` * _ [ ] ( ) < > | #` are backslash-escaped, newlines collapsed; no raw HTML, no links. The file states "Prepared from your own records by fiscl; not tax advice."
- **`redact_descriptions = true`** removes the merchant and note columns from the detail CSV (columns kept, cells empty) and says so in `notes`.
- Errors: `invalid` (bad format enum, year outside 2000..today.year+1), `not_found` (unknown business), `exists`, `invalid` with "the exports folder isn't a private directory inside your data folder; run fiscl doctor" when the lstat/ownership check fails.

### Changed tool: `estimated_tax` (READ_ONLY)
Args add `state_income_tax_rate_pct: number?` (overrides config; 0–20) and `state: str?` (two-letter, overrides config). With slice D it sums every business's `net_profit` (Schedule SE combines all self-employment) and adds `by_business: [{business, net_profit}]`.
Response additions:
```json
"state": {
  "code": "CA", "name": "California",
  "no_income_tax": false,
  "rate_pct": "6",                                        // null when not supplied
  "income_tax_estimate": {...} | null,                    // round_half_even(taxable × rate / 100), same taxable base as federal
  "installments": [ {"date": "2026-04-15", "pct": "30", "amount": {...}, "passed": true}, ... ],
  "verified_for": 2026,                                   // table year; a note when year ≠ verified_for
  "notes": ["States define taxable income differently; this applies your planning rate to the same base as the federal estimate.", ...]
} | null                                                  // null when no state is set
```
- No-income-tax states (table flag): `no_income_tax: true`, `income_tax_estimate: null`, `installments: []`, a note naming the state as having no broad personal income tax, plus any table `caveat` (e.g. Washington capital-gains tax, New Hampshire history). A supplied rate for such a state is ignored with a note.
- `projected_total` stays federal; new `projected_total_with_state` and `suggested_per_quarter_with_state` (state amounts follow the state's installment percentages, not equal quarters).
- Unknown year in the table: use the table's dates shifted to `year` with a note "verify this year's dates with your state".

### New data table: `tax/states.py`
```python
STATES: dict[str, StateInfo]  # all 50 + DC
@dataclass(frozen=True)
class StateInfo:
    name: str
    no_income_tax: bool
    installments: tuple[tuple[str, str], ...]   # ("MM-DD" with year offset, pct) e.g. (("04-15", "30"), ("06-15", "40"), ("01-15+1", "30"))
    caveat: str | None
    source: str                                  # URL of the state revenue page used
VERIFIED_FOR = 2026
```
Default installments for states that follow the federal schedule: `04-15, 06-15, 09-15, 01-15+1` at 25% each. Exceptions and the no-income-tax list come from the research doc (R3). Weekend/holiday shifts are **not** computed; a note says due dates move to the next business day.

### New tool: `record_1099` (W — `LOCAL_DESTRUCTIVE`: update/remove overwrite user data)
Module `tax/forms1099.py`.
Args:
```
{ "items": [ {
    "action": "add" | "update" | "remove",
    "id": int?,                         // required for update/remove
    "tax_year": int,                    // 2000..today.year+1
    "form": "nec" | "k" | "misc",
    "payer": str,                       // 1–80 chars after clean_text; stored, never in errors or audit text
    "amount": number,                   // box 1 (NEC), box 1a gross (K), or the user's chosen box (MISC); > 0
    "match_merchants": [str]?,          // 0–10 merchant names whose deposits are this payer's payments
    "business": str?,                   // slice D
    "note": str?                        // ≤ 200

```
Returns a plan per item (`before`/`after`, `id` for adds after apply). Errors: `not_found` (id), `invalid` (enum, amount ≤ 0, year), `exists` (same year+form+payer+business already added; use update).

### New tool: `reconcile_1099` (READ_ONLY)
Args: `{ tax_year?: int, business?: str (slice D) }`.
Response:
```json
{ "tax_year": 2026,
  "forms": [ {
      "id": 3, "form": "nec", "payer": "Acme Studio",
      "reported": {...},
      "matched_income": {...},                // business-scope income in the year from match_merchants (or payer name exact, case-insensitive, after merchant normalization)
      "matched_count": 7,
      "difference": {...},                    // reported − matched
      "status": "matches" | "reported_higher" | "reported_lower" | "no_matching_income",
      "questions": [ "The 1099-K gross can include fees, refunds, and sales tax that never reached your bank. Do you have the processor's annual summary?" ]
  } ],
  "unreported_payers": [ {"merchant": "Beta LLC", "income": {...}, "count": 3,
      "question": "You received business income from this payer but entered no 1099. That can be normal (below the reporting threshold, or paid by card); is it in your gross receipts?"} ],
  "totals": { "reported": {...}, "matched_income": {...}, "business_gross_receipts": {...} },
  "notes": [DISCLAIMER, "Matching uses the merchants you listed for each form…"],
  "meta": {...} }
```
- `matches` when |difference| ≤ $1.00. Question templates are fixed strings keyed by `(form, status)`: e.g. timing (December invoices paid in January), payer-name mismatch (suggest adding `match_merchants`), 1099-K gross vs net deposits, deposits landing in a personal-scope account (suggest `set_scope`), a payer listed on two forms (NEC and K for the same payment can double count).
- `unreported_payers`: business-scope income merchants in the year with total ≥ `tax.reporting_threshold_nec` for that year (table in `tax/forms1099.py`, values from the R4 research; phrased as "may be below the threshold", never "should have received").
- `payer` and `merchant` values are returned only as labeled data fields; they are untrusted (payer is user-typed, merchant is bank-derived).

### Multiple businesses (slice D; shape depends on the human decision, Option A assumed below)
- New tool `manage_business` (W — `LOCAL_DESTRUCTIVE`): `{action: add|rename|archive, name, new_name?, dry_run=true}`. Names 1–60 chars after `clean_text`, unique case-insensitively. The default business (id 1) can be renamed, never archived. Archiving a business with transactions in an open year is refused (`code="invalid"`).
- `set_scope` items gain optional `business: str`. Valid only with `scope = "business"` (transactions/merchants) or account scope `business`/`mixed`. Sets `business_id` on the targets. Existing calls without `business` behave exactly as today.
- `split_transaction` parts gain optional `business: str` (only with `scope: business`).
- New read tool `list_businesses` (READ_ONLY): `{}` → businesses with id, name, archived, accounts, YTD gross receipts and expenses.
- `schedule_c_draft`, `export_schedule_c`, `reconcile_1099`, `review_writeoffs` accept `business?`. `schedule_c_draft` without `business` when more than one active business exists returns `{"businesses": [<one draft per business>], "combined_net_profit": {...}}`; with exactly one business the response shape is unchanged from today (backward compatible for the single-business user and for existing tests).

### Migration 8 — businesses (slice D, Option A; only after the human decision)
```sql
-- 8 — v2 phase 3: multiple businesses. NULL business_id means "the account's business, else the default (id 1)".
-- Down: restore the pre-migration backup (columns can be dropped on SQLite ≥3.35 but the txn_lines view must be
-- recreated from migration 3's definition first).
CREATE TABLE businesses (
    id         INTEGER PRIMARY KEY,
    name       TEXT NOT NULL UNIQUE COLLATE NOCASE,
    archived   INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);
INSERT INTO businesses (id, name, created_at) VALUES (1, 'My business', datetime('now'));
ALTER TABLE accounts     ADD COLUMN business_id INTEGER REFERENCES businesses(id);
ALTER TABLE transactions ADD COLUMN business_id INTEGER REFERENCES businesses(id);
ALTER TABLE splits       ADD COLUMN business_id INTEGER REFERENCES businesses(id);
ALTER TABLE forms_1099   ADD COLUMN business_id INTEGER REFERENCES businesses(id);
-- forms_1099 uniqueness now includes the business
DROP INDEX ux_forms_1099;
CREATE UNIQUE INDEX ux_forms_1099_biz ON forms_1099 (tax_year, form, payer COLLATE NOCASE, COALESCE(business_id, 1));
CREATE INDEX ix_txn_business ON transactions(business_id);
DROP VIEW txn_lines;
CREATE VIEW txn_lines AS
SELECT t.id AS id, NULL AS split_id, t.account_id, t.posted_date, t.amount, t.currency,
       t.raw_description, t.merchant, t.memo, t.category_id, t.category_source, t.scope,
       t.transfer_group, t.is_pending, t.note, t.import_id, t.business_id
  FROM transactions t
 WHERE NOT EXISTS (SELECT 1 FROM splits s WHERE s.transaction_id = t.id)
UNION ALL
SELECT t.id, s.id, t.account_id, t.posted_date, s.amount, t.currency,
       t.raw_description, t.merchant, t.memo, s.category_id, 'manual', COALESCE(s.scope, t.scope),
       t.transfer_group, t.is_pending, COALESCE(s.note, t.note), t.import_id, COALESCE(s.business_id, t.business_id)
  FROM splits s JOIN transactions t ON t.id = s.transaction_id;
```
- Migration 7 deliberately uses a named unique index (not an inline `UNIQUE`) so migration 8 can swap it for the business-aware index without a table rebuild.
- `db.py` adds `BUSINESS_SQL = "COALESCE(t.business_id, a.business_id, 1)"` next to `SCOPE_SQL`, documented as meaningful only where `SCOPE_SQL = 'business'`.
- Backfill: none needed. Every existing row has NULL → default business, so a single-business database produces byte-identical Schedule C numbers (a test pins this).
- If the human picks Option B (account-level only), migration 8 adds only `businesses` + `accounts.business_id`; `txn_lines` is unchanged; `set_scope`'s `business` field applies to accounts only; split/transaction-level assignment is dropped from the contract.

## Risks & open questions
- **R1. Multiple-business data model.** Two options:
  - **Option A (recommended): `businesses` table + nullable `business_id` on accounts, transactions, splits (and 1099 forms).** Effective business = split → transaction → account → default (id 1). Pros: handles one card used for two businesses, split purchases across businesses, and per-row rules; NULL-means-default keeps every existing DB and test identical with no backfill. Cons: one more column in `txn_lines`, a view rebuild, and every business-scoped query uses `BUSINESS_SQL`.
  - **Option B: account-level only (`accounts.business_id`).** Each business must use its own accounts; transactions inherit. Pros: smallest change, no view rebuild, simplest mental model. Cons: mixed or personal cards used for business can only map to one business; splitting a purchase across businesses is impossible; users would have to open accounts to model reality.
  - Recommended answer: **Option A**, because mixed-account freelancers are fiscl's core user and `scope` already works at transaction and split level, so business should too. **Needs human decision? Yes** (blocks slice D only). Record the choice in `docs/decisions/DECISIONS.md`.
- **R2. Home office source of truth (config vs a tool).** Config only means the model can't set it; users edit TOML. → Recommended: config only in this phase (it's entered once a year, mirrors `income_tax_rate_pct`), plus a clear note in `schedule_c_draft` when missing. A `set_home_office` tool can come later through `config.append_toml_block`. Needs human decision? No.
- **R3. State due dates and installment percentages drift and have exceptions** (e.g. states with three or four installments, non-25% splits, different dates, no-income-tax states with special taxes). Facts in this spec (CA 30/40/0/30, the no-income-tax list AK, FL, NV, NH, SD, TN, TX, WA, WY with WA/NH caveats) are from memory and **must be verified**. → Recommended: run `my-skills:researcher` to produce the 51-entry table with official source URLs for tax year 2026 before slice B; ship with `VERIFIED_FOR = 2026` and a note when the year differs. Needs human decision? No (research task).
- **R4. 1099 reporting thresholds changed recently** (believed: 1099-NEC/MISC threshold rising from $600 to $2,000 for payments after 2025, and the 1099-K threshold reverting to $20,000 and 200 transactions). Unverified. → Recommended: same researcher pass confirms thresholds by year; keep them in a table in `tax/forms1099.py`; phrase `unreported_payers` as "may be below the threshold". Needs human decision? No.
- **R5. Export files outlive the user's intent.** They hold sensitive data outside the DB, are not rotated, and a cloud-synced data dir would sync them. → Recommended: 0600 files, doctor checks, a note in every export response ("delete exports you've sent to your preparer; fiscl doesn't remove them"), and the existing cloud-sync warning. No auto-deletion. Needs human decision? No.
- **R6. Simplified-method rules simplified further** (part-year use via `months_used` average, one home only, gross-income limit, no carryover). → Recommended: implement exactly those, and state in notes that a second home, the regular method, and daycare rules are out of scope. Needs human decision? No.
- **R7. Payer-to-merchant matching misses.** Bank deposits often show processor names (Stripe, PayPal) rather than the client. → Recommended: `match_merchants` is user-supplied; when empty, match only on an exact normalized payer name, and when nothing matches ask "Which deposits are from this payer?" rather than guessing. Needs human decision? No.
- **R8. PDF export.** → Recommended: later, behind a decision on a dependency (or a stdlib-only minimal PDF writer). Out of this phase. Needs human decision? No (deferred).
- **R9. Should `export_schedule_c` be dry-run by default?** It only adds files. → Recommended: yes, for consistency with every other write tool and so the model shows the planned filenames first. Needs human decision? No.
